Update flow (current implementation)

1) Service Worker registration (app/index.html)
- On page load, the app registers `../sw.js`.
- This enables the browser to manage SW versions (install/wait/activate).

2) Update detection (app/src/js/cache-update.js)
- On window `load`, the script waits for `navigator.serviceWorker.ready`.
- It calls `checkForUpdates()` which does:
  - `navigator.serviceWorker.getRegistration()`
  - `registration.update()` (browser checks if `sw.js` changed)
  - then waits a bit
  - scans existing app caches (names starting with `notoj-app-cache-v`)
  - compares the “current” cache vs the “latest” cache
- If a newer cache/version exists, it sets `updateAvailable=true` and updates the UI element `#updateCacheText` to show “Update available”.

3) “Update” button (user-controlled) (app/src/js/cache-update.js)
- When the user clicks “Update Now”, `performUpdate()` runs:
  - Sets `userTriggeredUpdate=true`
  - Calls `registration.update()` again to ensure the latest SW is fetched/installed by the browser
  - Selects the SW in state `registration.waiting || installing || active`
  - Sends `sw.postMessage({ type: 'SKIP_WAITING' })`

4) Apply new SW version (Service Worker message handlers)
- The current `sw.js` listens for `message` events:
  - `SKIP_WAITING` => `self.skipWaiting()` (moves the new SW from waiting to activate sooner)
  - `CLAIM_CLIENTS` => `self.clients.claim()` (new SW takes control of already-open pages)
  - `CLEAR_CACHE`, `CACHE_URLS`, `GET_CACHE_SIZE` are also supported

5) Reload to start the new version
- After posting `SKIP_WAITING` and then `CLAIM_CLIENTS` (when `registration.active` exists),
  - it waits for a `controllerchange` event (or times out)
  - sets UI back to “not updated”
  - calls `window.location.reload()` after ~1.2s

What this means right now
- Detection: automatic/lightweight, but it can cause the browser to fetch a new `sw.js` and the app’s cache versioning may affect “update available” state.
- Apply: fully user-controlled via the Update Now click, which triggers SKIP_WAITING + CLAIM_CLIENTS and then reload.
- Session safety: until the click, the app continues running on the currently controlled SW.
